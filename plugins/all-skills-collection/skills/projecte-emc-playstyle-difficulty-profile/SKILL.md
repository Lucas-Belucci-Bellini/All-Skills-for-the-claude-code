# EMC Playstyle and Difficulty Profile

## Purpose

player count, automation tolerance, exploration emphasis, desired pace, anchor items

## Required inputs

Translate preferences into concrete goals and representative anchor examples.

## Workflow

1. Confirm the actual Minecraft/loader/ProjectE versions and target config locations before interpreting recipe or item behavior.
2. Check goal conflicts and define what evidence would distinguish too-easy from too-grindy outcomes.
3. A balancing profile with anchors, constraints, and playtest scenarios.
4. Reproduce the candidate path with disposable fixtures or a calculation based on confirmed quantities; record runtime facts that could not be tested as unverified.
5. Produce do not present subjective preferences as measured results. with evidence, counts, status, and the next safe step.

## Validation checklist

- [ ] Version, registry, and source evidence are recorded.
- [ ] The full relevant route includes quantities, alternatives, remainders, and state changes.
- [ ] Suspected bypasses have a reproducible calculation or item-count comparison.
- [ ] Unknown quantities, chance outcomes, or runtime behavior are explicitly marked unknown.
- [ ] Live validation is bounded, backed up, and reversible.

## Required output

Do not present subjective preferences as measured results.

## Boundaries and failure handling

The pack should feel balanced rather than trivial or grind-heavy. A graph cycle or unusual yield is only a hypothesis until target recipe and state transitions support it. Stop when a safe minimal reproduction cannot be created without affecting production data.

## Trigger examples

- **Positive:** No balancing goal has been chosen.
- **Negative:** undefined
